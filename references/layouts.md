# Layout · 版式

> 回答：**这一页的空间怎么分。** 作用于单页，在 S3 分镜时逐页决定。

---

## §1 定义

Layout = **画布** + **区域** + 一种**骨架**。

- **画布**：页面的尺寸与安全区，由交付形态决定，全 deck 统一。
- **区域**：每页从上到下的固定分区（眉题、标题、主体、注释、页面 chrome）。
- **骨架**：主体区里的空间结构——内容是「一个焦点」「几个并列」「两方对比」还是「一条流程」。

Layout 只管「空间怎么分」，**不管**每块放什么部件（component）、何时出现（animation）、长什么颜色（theme）。所以同一个骨架可以承载完全不同的内容：`grid` 骨架既能放 4 张 KPI 卡，也能放 3 张功能卡。

## §2 规范（MUST）

### 2.1 画布

| 画布 | 设计尺寸 | 用于 | 安全区（内边距） | 实现方式 |
|---|---|---|---|---|
| **16:9** | 1920×1080 | `talk`；横版 `video` | 上下 72 / 左右 96 | `assets/base.css` 默认（`.slide` 撑满视口）；**以 1920×1080 窗口验收** |
| **9:16** | 1080×1920 | 竖版 `video` | 上 160 / 左右 72 / **底部 30% 不放主体内容** | 参照 `xhs-post` 的固定画布写法：给 `.deck` 与 `.slide` 设定固定宽高 |
| **3:4** | 810×1080 | `post` 图文 | 上下 70 / 左右 64 | 直接以 `templates/full-decks/xhs-post/` 为起点 |

- 全 deck 只用一种画布。
- 9:16 的底部 30% 会被平台界面与字幕遮挡，只允许放注释、来源、页脚。

### 2.2 区域

每页从上到下按下列顺序分区。**区域可以省略，但顺序不能调换**（`statement` 骨架例外，它只有一个大区）。

| 区域 | 放什么 | 现成类 |
|---|---|---|
| 眉题 | 章节标签、页面分类 | `.kicker` `.eyebrow` |
| 标题 | 本页 claim，一句话 | `.h1` `.h2` |
| 主体 | 一个骨架（见 2.3） | `.grid` `.row` `.stack` 等 |
| 注释 | 来源、补充、口播关键词 | `.lede` `.dim` `.dim2` |
| 页面 chrome | 页眉、页脚、页码、进度条 | `.deck-header` `.deck-footer` `.slide-number`（进度条由 runtime 自动注入） |

### 2.3 骨架

主体区只能是下列 8 种骨架之一（或按 §5 自创）。骨架名写进 `<section data-layout="...">`。

**`statement` 宣言** —— 纯排版的大字页：封面、章节页、金句、CTA、致谢

```
┌───────────────────────────┐
│ kicker                    │
│ ███████ 超大标题 ███████    │
│ lede                      │
│ [pill] [pill] [pill]      │
└───────────────────────────┘
```

**`focus` 焦点** —— 一个主视觉撑满主体：一个大数字、一张图表、一个大问号

```
┌───────────────────────────┐
│ kicker · 标题              │
│         ┌─────────┐       │
│         │  92%    │       │
│         └─────────┘       │
│ 注释 / 来源                │
└───────────────────────────┘
```

**`hero-detail` 主次** —— 一个主元素 + 一组支撑细节：结论 + 理由；大数字 + 分解

```
┌───────────────────────────┐
│ kicker · 标题              │
│ ┌──────────┐  · 细节 1     │
│ │  主元素   │  · 细节 2     │
│ └──────────┘  · 细节 3     │
└───────────────────────────┘
```

**`grid` 并列** —— 2~4 个同级元素等分（或 2×2）

```
┌───────────────────────────┐
│ kicker · 标题              │
│ ┌────┐ ┌────┐ ┌────┐      │
│ │ A  │ │ B  │ │ C  │      │
│ └────┘ └────┘ └────┘      │
└───────────────────────────┘
```

**`split` 对比** —— 两个对立面：A vs B、前 vs 后、优 vs 劣

```
┌───────────────────────────┐
│ kicker · 标题              │
│ ┌──────────┐┆┌──────────┐ │
│ │    A     │┆│    B     │ │
│ └──────────┘┆└──────────┘ │
└───────────────────────────┘
```

**`stack` 序列** —— 纵向排列的同类条目：清单、议程、排行、条形组、逐级推演

```
┌───────────────────────────┐
│ kicker · 标题              │
│ ▸ 条目 1 ─────────── 值    │
│ ▸ 条目 2 ─────────── 值    │
│ ▸ 条目 3 ─────────── 值    │
└───────────────────────────┘
```

**`flow` 流程** —— 节点 + 连接：时间线、步骤、管线、因果链、闭环

```
┌───────────────────────────┐
│ kicker · 标题              │
│ (1) ──→ (2) ──→ (3) ──→ (4)│
│ 说明    说明    说明   说明  │
└───────────────────────────┘
```

**`media` 图文** —— 图片、截图、代码块为主体，配少量标注

```
┌───────────────────────────┐
│ kicker · 标题              │
│ ┌─────────────────┐ 标注 1 │
│ │  图 / 代码       │ 标注 2 │
│ └─────────────────┘       │
└───────────────────────────┘
```

**画布变体**：在 9:16 画布上，`grid` 改为 2 列或单列、`split` 改为上下排列、`flow` 改为纵向，`hero-detail` 改为主元素在上、细节在下。骨架名不变。

### 2.4 字号档位

一页（不计页面 chrome）**最多用 3 个档位**。只用下表中的值。

| 档位 | 用途 | 16:9（1920 宽） | 9:16（1080 宽） | 现成类 |
|---|---|---|---|---|
| display | 超大数字、单字、封面巨字 | 160~220 px | 140~200 px | 无，写在页面 `<style>` 中 |
| h1 | 封面 / 章节标题 | 72 px | 80 px | `.h1` |
| h2 | 页标题 | 54 px | 60 px | `.h2` |
| h3 | 小节、大部件标题 | 32 px | 44 px | `.h3` |
| h4 | 卡片标题 | 22 px | 36 px | `.h4` |
| body | 正文、导语 | 18~22 px | 30~32 px | 默认 / `.lede` |
| caption | 注释、来源、标签 | 12~14 px | 22~24 px | `.kicker` `.eyebrow` `.pill` |

9:16 的值更大，是因为竖版视频在手机上观看，最小可读字号远高于投屏。

### 2.5 焦点、留白与对齐

- **一页一个焦点**：观众 1 秒内应能找到这页最重要的东西。焦点元素占主体区面积的 30%~60%。
- **留白**：主体区至少 20% 空白；内容少时宁可放大焦点，不要填满。
- **一条主对齐线**：默认左对齐；`statement` 与 `focus` 可居中。同一页不混用。
- **亲密性**：组内间距小于组间间距。组内用 `.mt-s`（8px）/ `.mt-m`（18px），组间用 `.mt-l`（32px）以上。

### 2.6 一致性

- 同一个 deck 里，**同一种 intent 的页用同一种骨架**，眉题、标题的位置保持不变——这是「重复」原则在版式上的落实。
- 变化来自内容与部件，而不是每页换一种骨架。

## §3 决策（SHOULD）

### 3.1 intent → 骨架

| 页面主 intent | 首选骨架 | 备选 | 说明 |
|---|---|---|---|
| `hook` | `statement` | `focus` | 一个问题 / 一个反常识数字 |
| `section` | `statement` | — | 章节名 + 编号 |
| `define` | `hero-detail` | `focus` | 术语为主，定义与要点为辅 |
| `claim` | `statement` | `hero-detail` | 结论本身就是焦点 |
| `evidence`（1 个数） | `focus` | `hero-detail` | 大数字 + 单位 + 来源 |
| `evidence`（多个数） | `grid` | `stack` | ≤4 个用 grid，更多用 stack |
| `evidence`（趋势） | `focus` | — | 一张图表占满主体 |
| `compare` | `split` | `grid` | 两方用 split，三方以上用 grid |
| `enumerate` | `grid` | `stack` | 同等重要且 ≤4 条用 grid；有先后或 >4 条用 stack |
| `sequence` | `flow` | `stack` | 步骤短用 flow，步骤带说明用 stack |
| `cause` | `flow` | `hero-detail` | 链式用 flow，一因多果用 hero-detail |
| `derive` | `stack` | `hero-detail` | 每一级算式一行，逐级向下 |
| `caveat` | `hero-detail` | `split` | 前提 / 限定作为主元素 |
| `quote` | `statement` | — | 引文 + 出处 |
| `recap` | `grid` | `stack` | 回顾 3~4 个要点 |
| `cta` | `statement` | — | 一句号召 + 联系方式 |

### 3.2 数量修正

| 条目数 | 处理 |
|---|---|
| 1 | `focus` |
| 2 | `split` 或 `grid` 2 列 |
| 3~4 | `grid` |
| 5~8 | `stack`，或 `grid` 两行 |
| >8 | 拆成两页，或合并归类后再放 |

## §5 自创（author）

8 种骨架都不贴合时，可以新建，但必须：

1. **说清信息结构**：用一句话描述它和 8 种骨架的区别（例：「环形闭环：节点首尾相接，强调无法跳出」）。说不清，就说明应该用现有骨架。
2. **遵守画布与区域**：安全区、区域顺序、字号档位、一页一个焦点，全部照旧。
3. **起一个骨架名**，写进 `data-layout`，并登记到分镜的「自创记录」。
4. **全 deck 复用**：同一 deck 里再遇到同类页面，用同一骨架、同一实现。
5. 页面级 CSS 写在 deck `<head>` 的 `<style>` 中，用 `.slide[data-layout="<名称>"]` 作用域，只引用 token。
